# 보행 네트워크 연동과 현장 운영 명세

[설계 개요](README.md) · [수요모델·현장 연구](research-protocol.md) · [교환 사양](contract/demand-v1.schema.json) · [검산 예제](contract/example.json)

현장 인수의 첫 질문은 **한 사람을 기준으로 공연장 출구를 떠나는 시각, 길 위의 위치, 목적지에 도착하는 시각을 서로 구분할 수 있는가**다. 수요 모듈은 출구를 떠나는 인원을 낸다. 보행 엔진은 그 사람들이 링크를 통과하고 대기하는 과정을 계산한다. 교통 통계는 그중 일부와 일반 이용객이 나중에 관측 지점을 통과한 결과다.

**현재 실행 경로.** Python의 `olpark_demand.egress build`가 회차별 방문·귀가 비중과 첫 목적지별 출발 인원을 `olpark-demand/1.1`로 발행한다. TypeScript의 `loadDemandSimulation`은 같은 파일을 받아 공통 링크의 대기와 목적지 도착을 계산한다. 명령행과 운영 화면에서 이 경로를 호출할 수 있다. 아래 1절은 연동 전 베이스 커밋의 조사 기록이다. ## 2. 무엇을 기존 엔진에 넘길 수 있는가

1. **기존 파일 호환.** A팀이 만드는 `events.json`, `prediction.json`, `notices.json`과 B팀의 `network/routes/parking/assumptions`를 같은 릴리스에서 검증한다. 기존 `schemaVersion: 1`은 이 파일 묶음의 번호다. 신규 교환 패킷의 버전은 `olpark-demand/1.0`이다. 로더가 생산자·소비자 지원 버전을 확인하고 지원 기능을 응답에 기록한다.
2. **기존 경로의 재현 가능 영역.** 단일 DOME 회차·전체 경로 개방을 우선 대상으로 한다. 철도에 배정한 인원이 `N_rail × 출발시각비중 × 고정출구비중 × 방면비중`으로 표현되고 출발 곡선·시간원점까지 일치해야 기존 엔진이 같은 OD를 낸다. 차량을 포함하면 사람 기준 `vehicle.ratio`와 분모, 탑승인원·지연·시간창 가정이 추가로 일치해야 한다. 철도 배정분만 계산한 결과에는 전체 인원과 계산된 인원을 같이 표시한다. 어댑터는 원래 OD와 재조합 OD의 셀별·주변합 오차를 반환한다.
3. **정보가 사라지는 요청.** 혼합 공연장, 시간에 따라 달라지는 방면, 출구별 다른 목적지, 교차로 폐쇄, 버스·주차·택시·도보 목적지, 미정 인원은 현재 파일 하나로 전부 표현할 수 없다. 해당 사례에는 지원되는 구간의 시나리오와 미배정 규모를 회신한다. 그 공백이 운영안의 우열을 바꾸는 요청은 현장 추천을 보류한다.
4. **다음 엔진.** 등록된 회차·출구별 주입, 시간가변 경로 유효성, 목적지 종류 확장, 승용차 탑승 전 보행, 잔류·미배정 장부를 먼저 구현한다. 기존 엔진과 새 엔진을 일치 가능한 단일 공연에 나란히 실행한다. 비교 범위를 통과하면 다회차·새 목적지 기능을 장소별로 연다.

**기존 코드에서 실제 재현한 경계 사례.** 사용자 분율 `[0.1, 0.2, 0.3, 0.4]`에 2분 창을 주면 현 분율 함수는 `[1/3, 2/3]`을 낸다. 두 출구 비중이 40/60인 100명 시험에서 첫 출구의 모든 경로만 막으면 현 엔진 장부에 60명만 주입된다. 경로가 모두 막히면 계산이 실패한다. 현 `clearMinute`는 **마지막 대기열이 풀리는 시각**이므로 아직 보행 중인 인원이 있어도 0이 될 수 있다. 신규 결과는 잔류·보행 중·목적지 도착·대기 해소를 각각 집계한다. 기준 커밋의 데이터 검증 4건, 기존 테스트 77건, 차량 시각 감사 3건이 통과한 상태에서 재현했다. ## 3. 교환 계약과 수지 검산

하나의 패킷은 **동일 예측 시각, 수요 시나리오 하나, 연속 시간창 하나, 영향을 함께 받는 회차들**을 나타낸다. 한 판단에서 비교할 두 운영안은 같은 패킷을 공유한다. 확률 비교는 같은 `draw_set_id`의 공동 표본들을 각각 엔진에 넣은 후 산출한다. 여러 칸의 q90을 모아 새로운 90% 상황으로 만들면 안 된다. [JSON Schema](contract/demand-v1.schema.json)

| 필드 | 생산 규칙 | 소비 규칙 |
|---|---|---|
| `run_id, supersedes_run_id, as_of, issued_at, usage` | 예측의 고유 ID, 이전 판본, 정보 절단점, 실제 발행시각, 가상/재생/그림자/운영 용도를 기록. 같은 입력 서명과 난수로 재생 가능하게 한다. | 승인된 용도와 장소만 운영 화면에 표시한다. 늦게 도착한 과거 실행이 최신판을 덮지 않게 한다. |
| `versions, scenario` | 네트워크 리비전·매핑·통행 상태·원자료·모델 묶음·주최사 입력·가정·생산 코드 버전, 시나리오 종류·난수·근거 ID를 고정한다. | 버전이 일치하는 등록부에서 이름과 경로를 찾는다. 운영자 조건 시나리오와 보정된 확률 표본에 다른 표식을 쓴다. |
| `horizon` | KST 오프셋을 가진 시작·끝, 5분, `venue_exit_departure`, `persons`. 시작 포함·끝 제외. | 조회 날짜가 넘어가도 절대시각을 기준으로 합친다. 출발 시각은 역 승차·차량 게이트 통과 시각과 구별한다. |
| `events[].od` | `event_id, event_revision, venue_id`에 귀속된 `origin_node_id, destination_node_id, first_mode, departure_start, persons`. 같은 회차의 같은 키는 한 번만 센다. | 첫 수단(철도·버스·주차 차량·택시/픽업·도보), 출발 노드의 해당 공연장 귀속, 목적지 종류, 출발 시 유효한 경로를 모두 확인한다. |
| `events[].unrouted` | 미등록 출구/목적지, 폐쇄, 도달 불가, 수단 미정, 출발시각 미확정별 인원과 근거. 알 수 없는 노드·시각은 허용된 공란으로 둔다. | 가능한 총수요 안에 남겨 둔다. 원인별 수치와 운영 민감도를 화면에 표시하고 승인된 수정에서만 새 경로에 배정한다. |
| `events[].ledger, totals` | 회차별·전체 인원을 같은 식으로 검산한다. 창 전 출발, 창 내 경로 배정, 창 내 미배정, 창 뒤 잔류의 합은 총원과 같아야 한다. | OD 합, 미배정 합, 회차 합을 독립적으로 다시 계산한다. 입장 전 취소는 0, 입장 뒤 취소는 실제 잔여 퇴장 집단을 유지한다. |

가상 예제는 자정을 넘는 두 공연의 144명을 담는다. 창 전 출발 14명, 창 안 경로 배정 80명, 창 안 미배정 38명, 창 뒤 잔류 12명이다. 배정된 사람은 23:55 DOME 남측→A 48명과 00:00 동측→B 32명이다. 미배정에는 P1 보행 접근점이 없는 10명, 첫 수단 미정 10명, 출구가 등록되지 않은 올림픽홀의 18명이 들어 있다. 동2문의 1시간 총출차 전망 35대는 위 144명의 어느 항목에도 더해지지 않는다. [가상 입력](contract/example.json)

**재예측 경계.** 23:57에 수정이 접수되면 새 5분 예측창은 다음 경계인 00:00에 시작하도록 설계한다. 23:57 이전에 관측된 출발과 23:57~00:00의 임시 추정을 구별해 경계 상태와 창 전 장부에 포함한다. 자정 뒤에도 같은 회차 키를 사용한다. 수정 시각이 꼭 5분 경계라면 그 시각부터 새 판본을 쓴다. 두 판본이 겹치는 구간의 인원을 더하지 않는다.

저장소 루트에서 다음처럼 명세와 의미 검사를 함께 실행할 수 있다. Python 3.12, `jsonschema` 4.26.0에서 검증했다. 예제 검사기는 고정된 소규모 경로 등록부를 사용한다. 운영 소비자는 실제 버전의 노드·폐쇄·행사 등록부로 같은 검사를 수행해야 한다. [예제 검사기](contract/validate_example.py)

```sh
python docs/design/egress-demand/contract/validate_example.py --self-test
```

## 4. 엔진 변경 순서와 물리적 보존

**공간 매핑.** B팀은 노드 키·시설 키·상위 장소·노드 종류·방향·접근성·좌표 및 좌표계·유효 시작/끝·근거를 제공한다. 현재 경위도 배열은 `[경도, 위도]` 순서다. 수요 팀은 교통기관 지점·호선·노선·방향과 모델 목적지의 대응표를 관리한다. 예를 들어 ‘올림픽공원역’에는 역·호선 관측점 두 개와 별개의 조건부 지상 접근점이 있다. 이름만 일치하는 연결은 운영 대상에서 보류한다. 주차구역에는 보행 접근 노드, 사용 가능한 차량문, 가능 용량, 시간에 따른 폐쇄가 각각 필요하다. 택시·픽업과 정류장은 정차/승차 가능 지점까지 검수한다. 하나의 측정점이 여러 경로를 보면 관측행렬에 그 사실을 남긴다. [현재 자산 정의][bundle]

**시간 변환과 도착.** 운영 입력은 5분 출발 합이고 엔진 계산은 1분이다. 분내 관측이 없을 때는 균등 분할을 가정으로 표시한다. 정수 인원 실행에서는 몫을 먼저 배분하고 남은 인원을 고정된 순서·난수로 배분한다. 관측 기반 분내 분포도 같은 5분 합을 유지해야 한다. 창을 늘려도 같은 출발분의 인원과 이미 소진된 사람 수는 동일해야 한다. 엔진은 경로 길이·속도·대기시간으로 도착을 계산한다. 수요모델이 승차 데이터를 출발시각으로 환산할 때 쓴 지연을 엔진 입력에 다시 더하지 않는다.

**사람 장부.** 매 시각 누적 출발 중 경로에 주입한 인원은 ‘링크·노드 이동 중 + 대기 중 + 첫 목적지 도착’과 일치해야 한다. 이동 중과 대기 중은 상호 배타적으로 정의한다. 미배정은 주입 전 장부에 남긴다. 계산 종료 때 출발하지 않은 인원, 이미 출발했으나 도착하지 않은 인원, 미배정 인원을 별개로 반환한다. 운영 중 재계산은 경계 시각의 실제/추정 장내 인원, 링크별 이동·대기 상태, 이미 도착한 인원, 주차 탑승 집단과 차량 대기를 함께 이어받는다. 상태가 없어 재생한 결과에는 재생 시작시각과 초기 상태 가정을 표시한다.

**승용차와 배경 통행.** 관객은 출구에서 주차장 접근점까지 보행 흐름에 포함하고, 도착 뒤 탑승 지연과 일행 구성을 통해 차량 대기열로 연결한다. 개인마다 독립적으로 차량 1대를 생성하면 과대계상된다. 일행·차량 표본에서 구한 조건부 탑승인원 분포와 실제 주차 상태를 사용하고 승차 준비 중인 잔여 인원을 기록한다. 승인된 배경 차량 유입은 다른 흐름으로 보태고 차량문에서 합산한 최종 통과량을 외부 총출차와 검산한다. 포화된 문에서 시각별 통과량은 대기열 유입량을 과소대표할 수 있다. 이용 대수 가정이 실제 점유·용량과 충돌하면 미설명 차이와 대체 구역/공원 외 주차 가정을 보고한다. 용량에서 잘려 사라진 사람을 승인 처리하지 않는다. [현재 보행·차량 분리 구현][sim-veh]

**운영 시나리오.** 정보 기준시각에 알려진 통제는 수요 배분과 엔진의 기본 조건을 같은 버전에 맞춘다. 그 뒤 현장 담당자가 비교하는 새 통제·안내는 별도의 계획 ID로 둔다. 안내 전환·순응도·폭 축소·신호 배분은 한 번만 적용한다. 폐쇄 시점에 이미 길 위에 있는 인원은 해당 위치에서 승인된 우회 또는 대기 상태로 이어간다. 접근성 제약을 충족할 경로가 확인되지 않으면 대체 지원이 필요한 인원을 표시한다. `clearMinute` 외에 ‘실제 도착 T50/T90/T95’, 창 종료의 미도착 인원, 최대 대기, 누적 대기(명·분/대·분), 추가 보행, 미배정 인원을 제공한다. 표지·안내의 실행은 권한 있는 담당자가 결정한다.

## 5. 서비스·저장·판본 관리

초기 운영 구성은 기존 TypeScript 엔진과 화면, Python 수요 학습·추론 작업자, 가벼운 HTTP API, PostgreSQL과 불변 객체 저장소다. 지리적 결합·버전 검사에 공간 질의가 필요할 때 PostGIS를 사용한다. 오프라인 학습과 온라인 실행은 같은 특성 변환 패키지와 시간 계약을 쓴다. 공연 등록·예측 실행 경로에서 원천 사이트나 대형 언어모델이 응답하기를 기다리지 않는다. 배포·장비는 장소별 업무량을 재어 정한다. 다음 표의 경로와 테이블은 구현 명세다.

회차 보강은 `POST /v2/events/{id}/enrich`에서 근거구절과 변경 제안을 반환하고 운영자 확정값은 별도 승인으로 개정한다. 수요 조건(비·인원·종료 지연)을 바꾸면 부모판을 가리키는 새 예측을, 동일 수요에서 안내 인력이나 경로만 바꾸면 새 `plan_run`을 만든다. 전반적인 실행 요청 ID와 개별 패킷의 `run_id`를 분리한다. 공동 표본 묶음에서 각 패킷은 유일한 `run_id`와 같은 `draw_set_id`, 서로 다른 `draw_index`를 가진다. 표본 수·예상 개수·완료 상태·해시를 담은 목록을 원자적으로 발행한 뒤 두 안이 같은 표본 전체를 참조했는지 확인한다.

`point-forecasts` 한 행에는 지점·원구간 시작/끝과 해상도, 인원/차량 단위, 총수요 점·구간, 비교 배경, 해당 조건의 증가분, 사용 모델·가용 자료·검증 상태를 둔다. 증가분의 구간은 짝을 이룬 전체·배경 표본의 차로 구한다. 버스 일 단위 정답에 시간 단위 모델이 있는 것처럼 표기하지 않는다. 운영 브리핑은 확정된 계산 결과의 숫자·단위·판본·근거를 서식으로 조합한다. 언어모델을 쓸 경우 생성문 속 숫자·범위·조치 근거를 원 결과에 대조하고, 불일치는 서식 문구로 돌린다.

**발행과 복구 순서.** 스냅샷 확정 → 특징 생성 → 예측·표본별 배분 → 구조·의미 검사 → 불변 결과 저장 → DB에서 발행 및 최신 포인터 비교·갱신 → 화면 통지 순이다. 객체 저장 뒤 DB 실패는 같은 실행 ID·해시로 재시도한다. 엔진 실패는 수요 예측의 원 결과에 영향을 주지 않는다. 한 작업자가 중단돼도 임차 만료 후 작업을 다시 받을 수 있게 하고, 승인과 발행은 비교 후 갱신으로 한 번만 성공시킨다. 새 일정·통제판이 먼저 발행됐다면 오래 걸린 구판의 결과는 과거 이력에만 둔다.

**권한과 비용.** 공단의 공연정보 등록·현장 운영, 모델 배포, 독립 검증에는 각각 필요한 권한을 부여한다. 주최사가 자료를 직접 제출하는 경우에는 해당 공연의 입력 권한만 부여한다. 실사용 서비스키는 서버의 비밀 저장소, 로컬 개발키는 로컬의 제한된 자격증명 저장소에서 읽는다. 브라우저 번들·원본 요청 로그·패킷·모델 카드에는 인증키를 넣지 않는다. 집계된 계수·설문 층 통계만 모델 학습층으로 보내고, 원천 계약상 재배포가 제한된 항목은 권한 있는 저장소 참조로 연결한다. 온라인 추론은 입력서명별로 캐시하고, 공연명 추출이나 시계열 가중치 변경은 성능·비용·사용 조건을 확인한 판본만 승격한다.

## 6. 운영 화면, 장애와 성능 목표

첫 화면에서 공단 담당자는 선택한 공연의 지도 위에 예상 병목 구간, 혼잡 시작·피크 시각, 예상 대기 인원을 확인한다. 같은 수요와 가용 인원에서 안전요원의 배치 위치나 안내 시작 시각을 바꾸면, 두 안의 구간별 대기시간·추가 보행거리·도착시간을 비교할 수 있게 한다. 지도에는 전체 예상 관객 가운데 경로가 연결된 인원과 미배정 사유를 표시한다. 경로가 비어 있는 방면은 ‘미확인’으로 표시한다.

회차·장소, 예측 기준·발행 시각, 결정 마감, 총원 범위와 출처, 실제로 관측한 시간·공간 단위를 함께 보여준다. 분포가 있는 예측에는 구간 폭과 경험적 포함률을 표시한다. 독립 현장 검증 전의 5분 배분은 ‘운영 가정’, 수신한 현장 계수는 ‘관측’으로 표시한다. 배치안 비교에는 변경한 조건, 필요한 인원, 대기가 늘어나는 구간과 시나리오도 남긴다.

현재 엔진의 대기·우회·차량 대기를 합산한 부담 점수에는 차량 탑승인원과 운영자의 목표가 들어간다. 보고서에서는 명·분, 대·분, 추가 보행, 필요한 인력, 적용 가능한 경로를 원단위로 함께 보여준다. 운영안 여럿을 탐색해 최솟값을 고를 때는 탐색용 표본과 최종 비교용 표본을 나눈다. 최종 비교용 묶음 안에서는 모든 안이 동일한 수요를 쓴다. 특정 수단이나 접근성 집단의 지연 증가 한도 등 현장 제약을 먼저 적용하고, 가정에 따라 순위가 바뀐 안은 어느 조건에서 바뀌었는지 표시한다. [기존 목적함수·계산][sim]

| 장애/변화 | 즉시 동작 | 복구 확인 |
|---|---|---|
| 날씨 발표 분량·교통 피드 지연 | 요청 시점과 마지막 수신시각의 차이·예보 대상시간을 표시. 검증된 축소 입력 모델 또는 ‘예측 보류’로 전환 | 누락/정정 도착 후 새 판본, 동일 가용성 조건에서 기준선 대조. 이미 봉인한 과거 예측은 유지 |
| 현장 계수기 단절·시계 오차·출구 개폐 | 관측 유효 끝을 표시. 마지막 판본 이후의 잔류·출발은 추정 범위로 제공. 개폐 검증 전 해당 경로 운영 추천 보류 | 계수기 시계·방향·연속성·중복 회복 검사. 필요한 구간은 재생하고 새 경계 상태로 시작 |
| 망 개정·미연결·시설 밖 목적지 증가 | 이전 망에서 경로 ID를 임의 치환하지 않는다. 버전이 맞는 부분 결과와 미배정 사유 반환 | B팀이 노드·경로 검수, 계약·현장 대조 후 신규 장소/목적지를 운영 허용 목록에 추가 |
| 계산 지연·모델 이상·사례 범위 밖 | 이전 최신 유효판의 기준시각·만료 상태를 노출. 검증된 기준선/수동 계획이 있는 지점은 해당 상태를 표시 | 화면까지의 실제 지연·대안 일치성 확인, 오류 원인 기록, 검증된 모델·보정·등록부 묶음으로 복귀 |
| 회차 취소·실제 종료 지연·동시 종료 | 진행 중인 사람을 보존하고 변경 시각 이후만 재계산. 같은 교통 지점을 공유하는 관련 회차를 함께 갱신 | 중복 발행·이미 출발한 인원 재주입·재입장 혼입 여부와 승인 대상을 확인 |

다음 수치는 **개발 부하 시험용 제안값**이다. 실제 지연 한도·입력 만료·동시 사용량은 현장 결정 마감에서 역산해 그림자 운영 전에 서명한다. 기본 프로필은 공연장 4곳의 동시 회차, 180분 창, 공동 표본 100개, 기본안·대안 2개, 동시 조회 20명으로 둔다. 저장 결과 조회 p95 2초 이내, 첫 중심 시나리오 발행 p95 10초, 표본 100개·두 안 전체 계산 p95 60초를 서로 다른 시계로 잰다. CPU/GPU 모델·메모리·콜드 스타트·표본 수·계산 실패율과 실제 벽시계 시간을 보고한다. 예산 내 불가능하면 표본 수에 따른 분위수와 운영안 순위의 안정성을 측정해 사용자에게 우선 결과와 완료 시간을 표시한다.

입력 완결률·시점 누락률·데이터 나이, 망 미배정 비중, 독립 정답 도착 뒤의 오차·구간 포함률, 그림자/운영 판본 별도 성능, 기한 내 발행률, 회차·지점별 대체 모델 사용률을 관측한다. 현장 계수 피드가 공표된 주기의 두 번 연속 비면 단절 경보를 내는 안으로 예행한다. 지연 자료의 수정 폭과 오류를 월평균에 묻지 않도록 대형·우천·동시 행사별로 따로 확인한다. 각 경보에는 수신 담당, 사용 가능 기능, 직전 승인판, 복구 시험을 연결한다.

## 7. 인수시험과 운영 승격

| 재현 입력 | 반드시 관찰할 결과 |
|---|---|
| 가상 예제 144명과 35대, 자정 양쪽 5분 칸 | 사람 장부 144명·배정 80명·미배정 38명, 차량문 35대 별도. 끝 시각에 시작하는 OD는 다음 창으로 이월 |
| 입장 전 취소 0명, 입장 뒤 취소, 앙코르 20분 지연 | 분모 0에서도 유효한 빈 결과. 입장 뒤 취소는 남은 퇴장 대상 유지. 새 판본이 이미 출발한 사람과 누적 관측을 이어받음 |
| DOME와 올림픽홀 동시 종료, 동일 역의 한 시간 정답 | 각 회차별 출발 장부·공통 링크의 합산 흐름·정답 한 건. 미등록 출구는 미배정으로 남음 |
| 단일 출구 전 경로 폐쇄, 모든 경로 폐쇄, 폭 축소/해제 시점, 접근성 경로 소실 | 정해진 경계 시각에 적용. 우회 승인 또는 대기·미배정으로 전량 설명. 모르게 삭제된 인원 0, 도달 불가 상태와 폐쇄 근거 표시 |
| 계산창 단축·연장, 5분을 1분으로 변환, 마지막 시각에 링크 이동 중 | 주입·출발 전후·이동 중·도착과 잔류가 보존되고 지난 구간 집계가 일치. 대기 해소와 전원 도착 지표가 구분됨 |
| 동일 노드명에 다른 장소 ID, 망/매핑 해시 불일치, 역 2개 호선과 출입구 1곳 | 잘못된 키는 검증 오류. 관측 두 개가 출구 두 곳으로 증식하지 않음. 사전 허용된 매핑 버전만 소비 |
| 주차 접근점 누락, 총출차와 공연 차량 겹침, 점유 초과, 일반 차량만 있는 날 | 탑승 전 보행 보존, 미설명·초과 인원 표시, 배경은 한 번만 반영. 차량 유입과 실제 게이트 통과가 따로 표시 |
| 관객 총원·출구별 출발 곡선·보행망·배치안을 고정하고, 주차장·대중교통·도보 귀가 방면의 비중만 변경 | 보행자가 같은 시간에 공통 통로에 도착하면 방면과 관계없이 합산한다. 분기 뒤에는 해당 방면의 인원만 흐른다. 시나리오별로 연결된 인원과 미배정 인원의 합을 확인한다. |
| 관측 0·미수신·공란, 사후 발표 날씨, 인증 만료, 중간 장애·동시 정정 | 가용시각 위반 차단, 빈 입력 상태 식별, 재시도·정정 순서 보존, 키 비노출, 이전 판본 재생 성공 |
| 동일 예측으로 기본안/대안 실행, 그림자 입력과 운영 입력 혼용 시도 | 동일 표본끼리 차이 비교. 동일 버전·난수에서 정한 수치 허용오차 내 재현. 모의 자료는 운영 지표·현장 발행에서 제외 |

교환 사양의 구조 검사는 JSON Schema가 맡고, 합계·시간창·관계·근거 인용은 별도 의미 검사가 맡는다. 동봉 예제 검사기는 정상 2건·오류 22건을 검사한다. 엔진 계산·운영 API·장애 복구는 위 표에 따라 별도의 인수시험을 구현해야 한다. 기존 파일 소비자를 보존하는 검증, 같은 예제의 Python 생산자/TypeScript 소비자 간 일치, 검측 현장의 생략 없는 통과 장부가 통합 완료 조건이다.

**승격과 복귀.** 데이터팀의 시점·결측 검수 → A/B팀 공동 계약과 엔진 인수 → 독립 담당자의 미래 공연 검증 → 현장 책임자의 장소·수단·시간대별 사용 승인 순이다. 수치 기준은 [연구 프로토콜](research-protocol.md)에 따라 실제 업무 손실과 독립 사례 수를 먼저 정한다. 적용 범위·유효기간·재검증일·복귀판을 배포 기록에 남긴다. 시간 역전·인원 비보존·잘못된 경로 버전 등 계약 위반이 있으면 해당 결과의 운영 발행을 멈춘다. 운영상 손실·구간 포함률·입력 신선도가 사전 합의선을 벗어나면 해당 출력만 기준선이나 수동 절차로 돌리고, 현장 책임자가 복구 시험 결과를 확인한다.
