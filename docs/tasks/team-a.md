# 팀원 A 작업 지시서 — 인원 예측 (AI)

> **AI에게 넘기는 방법**
> 이 파일, `docs/data-contract.md`(데이터 약속 문서), `PRODUCT.md`(서비스 소개) 세 개를 같이 주고
> "이 지시서대로 작업을 도와줘. 결과 파일은 반드시 data-contract.md의 모양을 지켜야 해."라고 말하면 됩니다.

---

## 1. 우리가 만드는 서비스

**OLPARK FLOW**는 올림픽공원에서 공연이 끝난 뒤 관객이 지하철역과 주차장으로 빠져나갈 때 **어느 길·출구에 줄이 생기는지 1분 단위로 계산해 보여주는 운영자용 웹 대시보드**입니다. 안내 방향과 출구 배정을 바꾼 "분산 운영안"이 지금 운영보다 얼마나 나은지도 비교합니다. 한국체육산업개발 공공데이터 활용 경진대회 시연용이며, 실제로 동작하는 계산이 가장 중요합니다.

서비스는 세 부분으로 나뉩니다.

| 부분 | 하는 일 | 담당 |
|---|---|---|
| **인원 예측 (AI)** | 이번 공연에 몇 명이, 언제, 어느 방향으로, 얼마나 차로 빠져나갈지 **예측** | **팀원 A (이 문서)** |
| 길 데이터 | 길의 연결·길이·폭, 주차장·출구 정보 | 팀원 B |
| 계산 엔진·화면 | 예측값과 길 데이터로 줄을 1분 단위로 **계산**하고 화면에 표시 | 통합 담당 |

**당신이 만든 예측값은 계산 엔진의 입력값이 됩니다.** 화면에는 "AI 예측" 배지와 함께 표시되고, 운영자는 이 값을 그대로 쓰거나 직접 바꿀 수 있습니다.

## 2. 맡은 일과 결과물

결과 파일은 모두 저장소의 `src/data/`에 넣습니다. 모양은 `docs/data-contract.md`의 1~3번 항목을 따릅니다.

| 결과물 | 내용 | 약속 문서 |
|---|---|---|
| `src/data/events.json` | 분석할 공연 목록 (공연장, 시작·종료 예정 시각, 좌석 수) | 1번 |
| `src/data/prediction.json` | 공연별 AI 예측 결과 | 2번 |
| `src/data/notices.json` | 올림픽공원 공지에서 뽑은 통제 구간 | 3번 |
| `ml/` 폴더 | 위 파일을 다시 만들 수 있는 코드 (Python 권장) | — |
| `docs/methods/prediction.md` | 어떤 데이터로, 어떤 방법으로 예측했는지 설명 (심사 발표용) | — |

### 2-1. 공연 목록 (`events.json`)
- 올림픽공원 공연장 4곳: KSPO DOME, 티켓링크 라이브 아레나, 올림픽홀, 우리금융아트홀
- 시작 시각과 **종료 예정 시각**이 필요합니다. 공연정보에 러닝타임이 있으면 `시작 + 러닝타임`, 없으면 장르별 평균 러닝타임을 쓰고 그 사실을 방법 문서에 적습니다.
- 공연명은 `"공연 A"`, `"공연 B"`처럼 바꿉니다. **결과 파일에 실제 아티스트명이 들어가면 안 됩니다.** 내부 작업에서는 써도 되지만, 이름과 공연 코드의 대응표는 저장소에 올리지 않습니다.

### 2-2. 예측 (`prediction.json`) — 핵심
공연 하나당 아래 값을 예측합니다. 각 값의 정확한 뜻과 규칙은 약속 문서 2번을 보세요.

| 예측할 값 | 쉬운 설명 | 아이디어 |
|---|---|---|
| `genre` | 공연 장르 + 확신도 + 근거 문장 | 공연명·소개글을 LLM이나 분류 모델로 판단. 근거 문장과 링크를 꼭 남김 |
| `attendance` | 관객 수 (가운데 값 + 아래·위 범위) | 좌석 수, 장르, 요일, 시간대, 과거 비슷한 공연 |
| `egressCurve` | 관객이 다 나오는 데 걸리는 시간, 가장 붐비는 시각 | 장르별 차이 (앙코르·굿즈 대기 등), 공연장 크기 |
| `directionShare` | 지하철 3개 방면으로 가는 비율 | 공연 종료 직후 역별 승하차 증가량의 비율 |
| `vehicle` | 차로 귀가하는 비율 | 공연 날 출차 대수 × 차 1대당 인원 ÷ 관객 수 |
| `similarEvents` | "근거 보기"에 보여줄 비슷한 과거 공연 5건 | 위 특징으로 가장 가까운 공연 찾기 |

**가장 어려운 점: "정답"(실제 관객 수)이 공개되지 않는 경우가 많습니다.** 그래서 대신 쓸 수 있는 지표(대리 지표)를 정하는 것이 첫 번째 일입니다. 예를 들어:
- 공연 종료 시간대에 주변 3개 역의 **승차 인원이 평소보다 늘어난 양**
- 공연 날 **주차장 출차 대수**
- 공연 시간대 **올림픽공원 일대 실시간 인구** 변화

어떤 대리 지표를 썼고 그 한계가 무엇인지는 반드시 방법 문서에 적어 주세요. 심사에서 가장 많이 받을 질문입니다.

**범위(`low`, `high`)는 정직하게.** 범위가 너무 좁으면 화면이 실제보다 확실한 것처럼 보입니다. 10%~90% 구간 등 어떻게 정했는지 `interval`과 방법 문서에 적습니다.

### 2-3. 공지에서 통제 구간 뽑기 (`notices.json`)
- 올림픽공원 공지사항에서 "보행로 통제", "공사", "부스 설치" 같은 내용을 찾아 구간·기간·내용·**근거 문장 원문**을 뽑습니다. LLM을 써도 됩니다.
- 근거 문장(`evidence.quote`)은 **원문 그대로** 넣습니다. 요약하거나 바꿔 쓰면 안 됩니다.
- 통제 구간이 지도에서 어느 길인지(`edgeIds`)는 **팀원 B가 만든 길 ID**를 씁니다. 모르면 비워 두고 `segmentName`만 적으면 됩니다.

## 3. 쓸 수 있는 데이터

대회에서 활용하기로 한 데이터입니다. 공공데이터포털(https://www.data.go.kr)과 서울 열린데이터광장(https://data.seoul.go.kr)에서 이름으로 검색하세요.

| 데이터 | 어디에 쓰나 |
|---|---|
| 한국체육산업개발 공연정보 | 공연 목록, 공연장, 일시, 장르 판단 |
| 한국체육산업개발 차량입출차 연계 | 차량 비율, 공연 날 출차 패턴 |
| 한국체육산업개발 실시간 주차현황 · 주차장 혼잡도 | 차량 비율 보조 지표 |
| 서울시 실시간 인구 | 공연 시간대 인구 변화 (관객 수 대리 지표) |
| 서울교통공사 승하차 | 방면 비율, 관객 수 대리 지표 |

- 데이터마다 **시간 단위**(1시간, 10분 등)가 다릅니다. 퇴장 곡선처럼 분 단위가 필요한 값을 1시간 단위 데이터로 추정했다면 그 한계를 적어 주세요.
- 다른 데이터를 추가로 쓰면 방법 문서에 출처를 적습니다. 화면 하단 출처 목록에도 추가해야 합니다.

## 4. 지켜야 할 것

1. **결과 파일의 모양은 약속 문서와 100% 같아야 합니다.** 필드 이름·단위·비율(0~1) 규칙을 지켜 주세요. 모양을 바꿔야 하면 먼저 통합 담당과 상의합니다.
2. 예측하지 못한 값은 지어내지 말고 `null`로 둡니다.
3. 실제 아티스트명·사진·로고는 결과 파일과 저장소에 넣지 않습니다.
4. 개인정보(이름, 연락처 등)가 들어간 원본 데이터는 저장소에 올리지 않습니다.
5. 코드는 `ml/` 폴더에만, 결과는 `src/data/`에만 넣습니다. 그 밖의 `src/` 폴더는 건드리지 않습니다.
6. 작업은 `data/team-a-…` 같은 이름의 브랜치에서 하고, PR로 올립니다.

## 5. 다 했는지 확인하는 기준

- [ ] `events.json`에 올림픽공원 공연장 공연이 1건 이상 있고, 시연할 공연(KSPO DOME · 공연 A)이 포함되어 있다
- [ ] `prediction.json`의 모든 공연에 대해 다음을 만족한다
  - [ ] `attendance.low ≤ value ≤ high`
  - [ ] `0 < egressCurve.peakMinute < egressCurve.totalMinutes`
  - [ ] `directionShare`의 A+B+C = 1 (소수점 오차 0.001 이내)
  - [ ] `vehicle.low ≤ ratio ≤ high`, 모두 0~1
  - [ ] `similarEvents`가 정확히 5건
  - [ ] `genre.sources`가 1건 이상이고 `quote`가 원문 그대로
- [ ] `notices.json`의 모든 항목에 근거 문장 원문과 링크가 있다
- [ ] 결과 파일 어디에도 실제 아티스트명이 없다
- [ ] `ml/README.md`에 적힌 명령 하나로 결과 파일을 처음부터 다시 만들 수 있다
- [ ] `docs/methods/prediction.md`에 사용 데이터, 대리 지표와 한계, 범위를 정한 방법이 적혀 있다

## 6. 추천 진행 순서

1. **데이터 확인** — 위 데이터를 내려받아 시간 단위, 기간, 빠진 값을 확인
2. **대리 지표 정하기** — 관객 수를 무엇으로 대신 볼지 정하고 통합 담당에게 공유
3. **첫 버전** — 간단한 방법(장르·공연장별 평균 등)으로 `prediction.json`을 먼저 끝까지 만들어 넘기기. 이것만 있어도 화면과 계산이 실제 값으로 돌아갑니다.
4. **정확도 올리기** — 모델 개선, 범위 보정, 비슷한 공연 찾기
5. **공지 추출** — `notices.json` (팀원 B와 길 ID 맞추기)
6. **방법 문서 정리** — 발표에 쓸 그림·표 포함

## 7. 함께 맞춰야 할 사람

- **통합 담당:** 결과 파일 모양, 화면에 보일 문구(장르 이름, 확신도 표현)
- **팀원 B:** 방면 A·B·C가 각각 어느 역 어느 출구인지 (A=올림픽공원역 3번, B=한성백제역 2번, C=몽촌토성역 1번), 통제 구간의 길 ID
