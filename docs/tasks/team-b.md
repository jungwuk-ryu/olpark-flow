## 1. 우리가 만드는 서비스

**OLPARK FLOW**는 올림픽공원에서 공연이 끝난 뒤 관객이 지하철역과 주차장으로 빠져나갈 때 **어느 길·출구에 줄이 생기는지 1분 단위로 계산해 보여주는 운영자용 웹 대시보드**입니다. 안내 방향과 출구 배정을 바꾼 "분산 운영안"이 지금 운영보다 얼마나 나은지도 비교합니다. 한국체육산업개발 공공데이터 활용 경진대회 시연용이며, 실제로 동작하는 계산이 가장 중요합니다.

| 부분 | 하는 일 | 담당 |
|---|---|---|
| 인원 예측 (AI) | 몇 명이, 언제, 어느 방향으로 빠져나갈지 예측 | 팀원 A |
| **길 데이터** | 길의 연결·길이·폭, 주차장·출구 정보, 계산 숫자의 근거, 검증 | **팀원 B (이 문서)** |
| 계산 엔진·화면 | 예측값과 길 데이터로 줄을 1분 단위로 계산하고 화면에 표시 | 통합 담당 |

### 계산 엔진은 당신의 데이터를 이렇게 씁니다
수도관에 물을 흘려보는 것과 같습니다. **길 = 수도관, 길 폭 = 관 굵기, 사람 = 물**입니다.

1. 공연장 출구에서 1분마다 사람이 나옵니다 (인원은 팀원 A의 예측).
2. 사람들은 `routes.json`에 적힌 길 토막을 순서대로 걸어갑니다. 걷는 시간 = 길이 ÷ 분당 70m.
3. 길 토막이 1분에 통과시킬 수 있는 사람 수 = **유효 폭(m) × 폭 1m당 1분 통과 인원(82명)**. 계단은 이보다 적습니다.
4. 들어오는 사람이 통과할 수 있는 사람보다 많으면 **줄**이 생깁니다.
5. 줄이 줄 설 공간(`queueAreaM2`)을 넘치면 그 앞 길까지 막힙니다.

예: 폭 2.4m 길은 1분에 약 197명이 지나갑니다. 1분에 350명이 오면 매분 150명씩 줄이 늘어납니다.
그래서 **폭이 결과를 가장 크게 좌우합니다.** 폭이 2.4m인지 4m인지에 따라 줄 길이가 두 배 가까이 달라집니다.

지금 `src/data/`에 들어 있는 길·폭은 통합 담당이 대충 넣은 가짜 값입니다. 당신이 이 값을 실제 값으로 바꾸면 계산 결과가 실제가 됩니다.

## 2. 할 일 상세

### 2-1. 길 뼈대 만들기 (`network.json`, `routes.json`) — A1 + B2·B3

길은 오픈스트리트맵·서울시 도보 네트워크에 이미 있습니다. 처음부터 그리지 않고 **가져와서 줄이고 이름을 붙입니다.** 아래 내용은 AI가 A1을 할 때의 규칙이자, B2·B3에서 확인할 기준입니다.

> 통합 담당이 오픈스트리트맵으로 만든 자동 뼈대가 `src/data/network.json`에 들어 있으면, 그것을 출발점으로 확인·수정만 하면 됩니다.

**범위:** KSPO DOME 출구 → 지하철역 지상 출입구 3곳

| 방면 | 도착점 |
|---|---|
| A | 올림픽공원역 3번 출구 (5·9호선) |
| B | 한성백제역 2번 출구 (9호선) |
| C | 몽촌토성역 1번 출구 (8호선) |

**순서**
1. (B2) 올림픽공원 공식 안내도와 KSPO DOME 시설 안내도로 **공연장 출구 위치와 개수**를 확인합니다.
2. (A1) 보행로 데이터에서 출구부터 각 역까지 경로를 찾고, 아래 지점에 점을 둡니다. (B3) 그 경로가 사람들이 실제로 많이 걷는 길인지 확인합니다.

| 점 종류 (`kind`) | 어디에 찍나 |
|---|---|
| `exit` 출구 | 공연장 출구마다 |
| `junction` 갈림길 | 방면이 나뉘는 곳 (예: 중앙 분기점) |
| `bottleneck` 병목 | 길이 좁아지는 곳, 문, 계단 시작점, 다리 |
| `crossing` 교차점 | 보행로가 차량 출구 길과 겹치는 곳 |
| `destination` 도착점 | 역 출입구 3곳 |

3. 점과 점 사이가 **길 토막**(`edges`)입니다. 폭·종류가 바뀌는 곳마다 토막을 나눕니다. 시연용으로는 길 토막 10~20개면 충분합니다.
4. 각 점의 좌표(위도·경도)를 적습니다. 지도에서 그 지점을 우클릭하면 좌표가 나옵니다.
5. `routes.json`에 출구별·방면별로 지나가는 길 토막을 순서대로 적습니다.
6. 출구별로 관객이 나오는 비율(`exitShare`)을 정합니다. 근거가 없으면 출구 폭 비율로 나누고 `"가정"`으로 표시합니다.

**규칙**
- 길 토막의 `from` → `to`는 **사람이 공연장에서 나가는 방향**입니다.
- ID는 한 번 정하면 바꾸지 않습니다 (팀원 A의 통제 구간이 이 ID를 씁니다).
- 지금 목업 파일(`src/data/network.json`)의 ID를 그대로 써도 되고, 새로 만들어도 됩니다. 새로 만들면 통합 담당에게 알려 주세요.

### 2-4. 계단·문·줄 설 공간
- **계단·문·경사로:** 로드뷰로 확인합니다. OSM에는 계단이 별도 선(`highway=steps`)으로 표시된 곳이 많아 먼저 보면 빠릅니다. 계단이 있으면 `type: "stairs"`, `stepFree: false`.

### 2-5. 주차장·차량 출구 (`parking.json`)
1. 주차장 P1~P7 대수: P1 562 · P2(올림픽홀 지하 포함) 320 · P4 117 · P5 176 · P6 167 · P7 137. **P3가 없는 게 맞는지** 실시간 주차현황 데이터로 확인합니다.

3. **출구 처리량 구하기 (차량입출차 연계 데이터):**
   1. 큰 공연이 있던 날을 여러 개 고릅니다.
   2. 공연 종료 후 0~60분의 출차 기록을 **출구별·1분 단위로** 셉니다.

   4. 데이터에 출구 구분이 없으면 전체 처리량을 출구 수로 나누고 `"가정"`으로 표시합니다.
4. 차량 출구 길이 보행로와 겹치는 교차점을 `crossingNodeIds`로 연결합니다.

|---|---|---|
| 걷는 속도 | 분당 70m | 군중 보행 속도 연구 |
| 폭 1m당 1분 통과 인원 | 통로 82명, 문 115명, 계단은 통로의 60% | 보행 서비스 수준(LOS) 문헌, 국내 보행 시설 설계 기준 |
| 날씨 보정 | 우천 0.85 | 우천 시 보행 속도·밀도 연구 |
| 꽉 막혔을 때 1인당 넓이 | 0.46㎡ | 군중 밀도·위험 기준 문헌 |
| 교차점 보행 비율 | 1분 중 60% | 교차점 통제 방식 (공원 안내·운영 자료) |
| 분기점당 안내요원 | 2명 | 행사 안전 관리 지침 |
| 주차장까지 걷는 시간 | 5분 | 지도로 공연장 → 주차장 평균 거리 ÷ 걷는 속도 |

### 2-7. 검증
"계산이 현실과 비슷하다"는 근거를 만드는 일입니다. 심사에서 가장 중요한 부분입니다.

**① 실제 데이터와 비교**
1. 큰 공연이 있던 날 몇 개를 고릅니다.
2. **서울교통공사 승하차:** 공연 종료 시간대에 3개 역 승차 인원이 평소(같은 요일·같은 시간, 공연 없는 날)보다 얼마나 늘었는지 구합니다.
   - 늘어난 양의 비율 → 실제 방면 비율 (팀원 A의 예측과 비교)
   - 늘어난 시간대 → 실제로 역에 도착한 시점 (계산의 도착 시각과 비교)
3. **서울시 실시간 인구:** 공연 직후 공원 일대 인구가 줄어드는 속도 → 계산의 대기 해소 시각과 비교
4. 차이가 크면 어떤 값(폭, 통과 인원, 출구 비율)을 바꾸면 맞는지 찾아 `assumptions.json`에 반영하고, 그 과정을 기록합니다.

**② 민감도 확인**
- 폭을 ±20% 바꿔 계산해도 "분산 운영안이 현재 운영안보다 낫다"는 결론이 같은지 확인합니다.
- 비교 명령은 통합 담당이 만들어 줄 예정입니다.

## 3. 길 폭 재는 법 (상세)

### 3-1. 무엇을 재나: "유효 폭"
**사람이 실제로 걸을 수 있는 폭**입니다. 길 전체 폭이 아닙니다.

```
 ┌───── 길 전체 폭 6.0m ─────┐
 │ 화단 │      걸을 수 있는 곳      │가로등│
 │ 1.5m │                          │ 0.5m │
 └──────┴──────────────────────────┴──────┘
          ↑ 측방 여유 0.3m     측방 여유 0.3m ↑
 유효 폭 = 6.0 − 1.5(화단) − 0.5(가로등) − 0.3 − 0.3 = 3.4m
```

- **화단·가로등·벤치·펜스·안내판·쓰레기통처럼 사람이 못 지나가는 부분을 뺍니다.**
- **측방 여유:** 사람은 벽·펜스·화단에 바짝 붙어 걷지 않습니다. 벽·펜스·화단 옆은 각각 약 0.3~0.5m를 더 뺍니다. 보행 연구에서 쓰는 개념이니, 정확한 값의 근거를 2-6에서 같이 찾아 주세요.
- 길 토막 안에서 폭이 달라지면 **가장 좁은 곳** 기준으로 적습니다. 그곳이 병목입니다.
- 국내 보도 설계 지침에 나오는 "유효 보도 폭" 정의를 확인해 기준으로 삼으면 좋습니다.

### 3-2. 도구

| 도구 | 쓰는 곳 | 비고 |
|---|---|---|
| **브이월드 항공영상** | 길 전체 폭 재기 | 해상도가 높아 보도 경계가 잘 보임. 거리 재기 도구 있음 |
| **카카오맵 스카이뷰 / 네이버 지도 위성** | 길 전체 폭 재기, 다른 시기 사진과 비교 | PC 웹의 거리 재기·면적 재기 사용 |
| **카카오 로드뷰 / 네이버 거리뷰** | 장애물 확인, 폭 추정 | 공원 안쪽 길은 로드뷰가 없을 수 있음 |
| **오픈스트리트맵(OSM)** | 계단 위치, 일부 길의 폭(`width` 태그) | 폭 태그는 드묾 |
| **QGIS** (무료) | 여러 길을 한 번에 관리, 면적 계산 | 선택 사항 |

로드뷰가 없는 공원 안쪽 길은 지도 앱의 사용자 사진·블로그 사진을 참고해 장애물을 확인합니다. 사진에서 폭을 재지는 말고, 장애물 위치와 종류만 봅니다.

### 3-3. 순서 (길 토막 하나당)
1. **가장 좁아 보이는 곳 찾기:** 항공사진을 확대해 길 토막을 따라가며 폭이 좁아지는 곳을 찾습니다.
2. **전체 폭 재기:** 거리 재기 도구로 **길과 수직 방향**으로, 보도 포장 경계에서 반대쪽 경계까지 잽니다. 같은 지점을 2~3번 재서 평균을 냅니다.
3. **장애물 확인:** 로드뷰로 같은 지점을 보고 화단·가로등·벤치·펜스의 위치와 대략적인 폭을 확인합니다.
4. **장애물 폭 추정:** 로드뷰에서 크기가 정해진 물체와 비교합니다.
   - 점자블록 한 장: 30cm × 30cm
   - 주차칸 폭: 약 2.5m (일반형 기준)
   - 보도블록은 규격이 여러 가지라, 같은 길의 블록 한 장 크기를 항공사진으로 먼저 확인한 뒤 자로 씁니다.
5. **유효 폭 계산:** 전체 폭 − 장애물 폭 − 측방 여유
6. **기록:** 아래 측정 기록에 적고, `network.json`의 `widthM`을 바꿉니다.

### 3-4. 계단·문은 따로
- **계단:** 계단 자체의 폭(난간 사이)을 잽니다. `type: "stairs"`. 계산 엔진이 평지보다 적게 통과시킵니다.
- **문(게이트):** 열리는 문 폭의 합을 잽니다. 예: 1.8m 문 4개 = 7.2m. `type: "gate"`. 공연 때 실제로 열리는 문만 셉니다 (공원·공연장 안내 자료로 확인).
- **역 출입구:** 계단 폭과 에스컬레이터 유무를 확인합니다. 에스컬레이터는 계단 폭에 넣지 않고 측정 기록에 따로 적습니다.

### 3-5. 측정 기록 남기기
나중에 "이 값은 어떻게 재셨나요?"에 답할 수 있도록 `geo/measurements.csv`에 남깁니다.

```csv
edgeId,widthTotalM,obstaclesM,shyM,widthEffectiveM,lengthM,areaM2,method,imageDate,confidence,memo
e-amerge-crossing,3.6,0.6,0.6,2.4,80,700,브이월드 항공영상+카카오 로드뷰,2025-05,중,화단 0.6m. 로드뷰 2024-10
```

| 열 | 뜻 |
|---|---|
| `widthTotalM` | 전체 폭 |
| `obstaclesM` | 빼는 장애물 폭 합 |
| `shyM` | 빼는 측방 여유 합 |
| `widthEffectiveM` | 유효 폭 (= `network.json`의 `widthM`) |
| `method` | 쓴 도구 |
| `imageDate` | 항공사진·로드뷰 촬영 시기 (사진마다 표시됨) |
| `confidence` | 확신도: 상(장애물까지 명확) / 중 / 하(사진이 흐리거나 가려짐) |

확신도가 "하"인 길은 2-7의 민감도 확인에서 특히 살펴봅니다.

### 3-6. 정확도 기준
- **병목 지점(`bottleneck`) 앞뒤 길:** 0.3m 이내를 목표로 2~3번 재서 평균
- **넓은 길(폭 6m 이상):** 0.5~1m 오차 괜찮음. 이런 길은 거의 막히지 않습니다.
- **길이:** 10m 이내
- **줄 설 공간 넓이:** 20% 이내

## 5. 지켜야 할 것

1. **결과 파일의 모양은 약속 문서와 100% 같아야 합니다.** 모양을 바꿔야 하면 먼저 통합 담당과 상의합니다.
2. 길·장소 ID는 한 번 정하면 바꾸지 않습니다. 바꿔야 하면 미리 알립니다.
3. 길 토막의 `from` → `to`는 **사람이 공연장에서 나가는 방향**입니다.
4. 측정하지 않은 값은 `source: "가정"`, 데이터로 확인한 값은 `"관측"`으로 표시합니다. 지도·항공사진으로 잰 폭도 실측이 아니므로 `"가정"`으로 두고, 측정 기록에 방법을 남깁니다.
5. 사람 얼굴·차량 번호판이 나온 사진은 저장소에 올리지 않습니다. 지도 서비스 화면 캡처도 이용약관을 확인한 뒤 올립니다.
6. 작업 파일은 `geo/`, 결과는 `src/data/`에만 넣습니다. 그 밖의 `src/` 폴더는 건드리지 않습니다.
7. 작업은 `data/team-b-…` 같은 이름의 브랜치에서 하고, PR 전에 **`pnpm validate:data`**를 돌립니다. 틀린 곳을 문장으로 알려 줍니다.
