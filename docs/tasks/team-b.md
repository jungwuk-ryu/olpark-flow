## 1. 우리가 만드는 서비스

**OLPARK FLOW**는 올림픽공원에서 공연이 끝난 뒤 관객이 지하철역과 주차장으로 빠져나갈 때 **어느 길·출구에 줄이 생기는지 1분 단위로 계산해 보여주는 운영자용 웹 대시보드**입니다. 안내 방향과 출구 배정을 바꾼 "분산 운영안"이 지금 운영보다 얼마나 나은지도 비교합니다. 한국체육산업개발 공공데이터 활용 경진대회 시연용이며, 실제로 동작하는 계산이 가장 중요합니다.

서비스는 세 부분으로 나뉩니다.

| 부분 | 하는 일 | 담당 |
|---|---|---|
| 인원 예측 (AI) | 몇 명이, 언제, 어느 방향으로 빠져나갈지 예측 | 팀원 A |
| **길 데이터** | 길의 연결·길이·폭, 주차장·출구 정보, 계산에 쓰는 가정값 | **팀원 B (이 문서)** |
| 계산 엔진·화면 | 예측값과 길 데이터로 줄을 1분 단위로 계산하고 화면에 표시 | 통합 담당 |

### 계산 엔진은 당신의 데이터를 이렇게 씁니다
수도관에 물을 흘려보는 것과 같습니다. **길 = 수도관, 길 폭 = 관 굵기, 사람 = 물**입니다.

1. 공연장 출구에서 1분마다 사람이 나옵니다 (인원은 팀원 A의 예측).
2. 사람들은 `routes.json`에 적힌 길 토막을 순서대로 걸어갑니다. 걷는 시간 = 길이 ÷ 분당 70m.
3. 길 토막 하나가 1분에 통과시킬 수 있는 사람 수 = **유효 폭(m) × 폭 1m당 1분 통과 인원**. 계단은 이보다 적습니다.
4. 들어오는 사람이 통과할 수 있는 사람보다 많으면 **줄**이 생깁니다.
5. 줄이 줄 설 공간(`queueAreaM2`)을 넘치면 그 앞 길까지 막힙니다.
6. 차량 출구와 겹치는 교차점에서는 1분을 보행자와 차가 나눠 씁니다.

그래서 **길 폭·길이·줄 설 공간·출구 처리량**이 결과를 가장 크게 좌우합니다. 이 값들의 정확도와 근거가 당신이 맡은 일의 핵심입니다.

## 2. 맡은 일과 결과물

결과 파일은 모두 저장소의 `src/data/`에 넣습니다. 모양은 `docs/data-contract.md`의 4~7번 항목을 따릅니다.

| 결과물 | 내용 | 약속 문서 |
|---|---|---|
| `src/data/network.json` | 보행 길 연결: 장소(점)와 길 토막(선) | 4번 |
| `src/data/routes.json` | 방면 A·B·C로 가는 길 토막 순서 | 5번 |
| `src/data/parking.json` | 주차장 P1~P7과 차량 출구 | 6번 |
| `src/data/assumptions.json` | 계산 공식에 들어가는 가정값과 근거 | 7번 |
| `geo/` 폴더 | 위 파일을 만든 코드나 작업 기록 (QGIS 프로젝트, 변환 스크립트 등) | — |
| `docs/methods/network.md` | 길 데이터를 어떻게 만들었고 값의 근거가 무엇인지 (심사 발표용) | — |

### 2-1. 보행 길 연결 (`network.json`)
범위는 **공연장 출구 → 지하철역 지상 출입구**까지입니다. 시연 대상인 KSPO DOME부터 하고, 나머지 공연장(티켓링크 라이브 아레나, 올림픽홀, 우리금융아트홀)은 여유가 되면 추가합니다.

| 넣어야 할 장소 (`nodes`) | 설명 |
|---|---|
| 공연장 출구 (`exit`) | 관객이 나오는 문. 출구별로 나오는 비율 `exitShare` (합 = 1) |
| 갈림길 (`junction`) | 방면이 나뉘는 곳 (예: 중앙 분기점) |
| 병목 (`bottleneck`) | 문, 계단, 좁은 다리처럼 줄이 생기기 쉬운 곳 |
| 교차점 (`crossing`) | 보행로와 차량 출구 길이 겹치는 곳 |
| 도착점 (`destination`) | A=올림픽공원역 3번 출구, B=한성백제역 2번 출구, C=몽촌토성역 1번 출구 |

길 토막(`edges`)마다 필요한 값:

| 값 | 구하는 방법 아이디어 |
|---|---|
| 길이 `lengthM` | 서울시 도보 네트워크, 지도에서 측정 |
| 유효 폭 `widthM` | 항공사진·로드뷰로 측정, 현장 확인. 화단·기둥·펜스를 뺀 **실제로 걸을 수 있는 폭** |
| 종류 `type` | 평지 / 계단 / 경사로 / 문 |
| 줄 설 공간 `queueAreaM2` | 그 길 끝(병목 앞)에서 사람이 기다릴 수 있는 광장·통로의 넓이 |
| 계단 없음 `stepFree` | 휠체어·유모차로 갈 수 있는지 |

- 좌표는 **위도·경도(WGS84)**로 넣습니다. 공공데이터가 TM 좌표(EPSG:5186, 5179 등)면 변환하고, 원래 좌표계를 `coordSystemOriginal`에 적습니다.
- GeoJSON이나 QGIS로 작업해도 됩니다. 넘길 때만 약속 문서 모양으로 바꾸거나, 원본을 주면 통합 담당이 변환합니다.
- **실측이 아닌 값은 `source: "가정"`**으로 표시합니다. 화면에 "시연용 가정값"으로 뜹니다. 실측했다면 `"관측"`입니다.

### 2-2. 방면별 경로 (`routes.json`)
- 공연장 출구에서 각 역까지 **실제로 사람들이 많이 가는 길**을 길 토막 ID 순서로 적습니다.
- 출구가 여러 개면 출구마다 경로를 적습니다. 여러 방면이 같은 길을 같이 써도 됩니다.

### 2-3. 주차장과 차량 출구 (`parking.json`)
- 주차장: P1 562대 · P2(올림픽홀 지하 포함) 320대 · P4 117대 · P5 176대 · P6 167대 · P7 137대. **P3가 없는 게 맞는지 확인해 주세요.**
- 차량 출구: 북2문 · 동2문 · 남2문 (다른 출구가 있으면 추가)
- 주차장마다 어느 출구로 나갈 수 있는지, 출구마다 **1분에 몇 대가 나갈 수 있는지**(`throughputPerMin`)
- 처리량은 **차량입출차 데이터의 공연 종료 직후 분당 출차 대수 최댓값**으로 추정하면 근거가 생깁니다. 그 데이터가 없으면 가정값으로 두고 표시합니다.
- 차량 출구 길이 보행로와 겹치는 교차점을 `crossingNodeIds`로 연결합니다.

### 2-4. 계산 가정값 (`assumptions.json`)
공식에 들어가는 숫자입니다. 지금은 임시값이 들어 있고, **근거를 찾아 고치는 것**이 당신의 일입니다.

| 값 | 지금 임시값 | 찾을 근거 |
|---|---|---|
| 걷는 속도 | 분당 70m | 군중 보행 속도 연구 |
| 폭 1m당 1분 통과 인원 | 통로 82명, 문 115명, 계단은 통로의 60% | 보행 서비스 수준(LOS) 문헌, 국내 보행 설계 기준 |
| 날씨 보정 | 우천 0.85 | 우천 시 보행 속도·밀도 연구 |
| 꽉 막혔을 때 1인당 넓이 | 0.46㎡ | 군중 밀도·위험 기준 문헌 |
| 교차점 보행 비율 | 1분 중 60% | 현장 신호·통제 방식 |

- 값마다 `notes`에 출처(문헌 이름, 쪽수, 링크)를 적어 주세요. 심사에서 "이 숫자는 어디서 왔나요?"에 답하는 근거가 됩니다.

## 3. 쓸 수 있는 데이터

공공데이터포털(https://www.data.go.kr)과 서울 열린데이터광장(https://data.seoul.go.kr)에서 이름으로 검색하세요.

| 데이터 | 어디에 쓰나 |
|---|---|
| 서울시 도보 네트워크 | 길 연결과 길이의 뼈대 |
| 한국체육산업개발 차량입출차 연계 | 출구별 분당 처리량 |
| 한국체육산업개발 실시간 주차현황 · 주차장 혼잡도 | 주차장 대수, 혼잡 패턴 |
| 서울교통공사 승하차 | 계산 결과 검증 (공연 후 역별 승차 증가와 비교) |
| 서울시 실시간 인구 | 계산 결과 검증 |
| 항공사진·로드뷰 (브이월드, 카카오·네이버 지도 등) | 유효 폭, 줄 설 공간 측정 |

- 도보 네트워크에는 **폭·계단 정보가 없을 수 있습니다.** 그러면 시연에 필요한 주요 경로(출구 → 중앙 분기점 → 3개 역)만 직접 측정하는 게 현실적입니다.

## 4. 지켜야 할 것

1. **결과 파일의 모양은 약속 문서와 100% 같아야 합니다.** 모양을 바꿔야 하면 먼저 통합 담당과 상의합니다.
2. 길·장소 ID는 한 번 정하면 바꾸지 않습니다. 팀원 A의 통제 구간과 경로가 이 ID를 씁니다. 바꿔야 하면 미리 알립니다.
3. 길 토막의 `from` → `to`는 **사람이 공연장에서 나가는 방향**입니다.
4. 실측이 아닌 값은 반드시 `"가정"`으로 표시합니다.
5. 사람 얼굴·차량 번호판이 나온 사진은 저장소에 올리지 않습니다.
6. 작업 코드·기록은 `geo/` 폴더에만, 결과는 `src/data/`에만 넣습니다. 그 밖의 `src/` 폴더는 건드리지 않습니다.
7. 작업은 `data/team-b-…` 같은 이름의 브랜치에서 하고, PR로 올립니다.

## 5. 다 했는지 확인하는 기준

- [ ] `network.json`
  - [ ] KSPO DOME의 모든 출구에서 3개 역 도착점까지 길이 이어져 있다 (끊긴 곳 없음)
  - [ ] 모든 길 토막의 `from`·`to`가 실제 있는 장소 ID다
  - [ ] 공연장별 출구의 `exitShare` 합이 1이다
  - [ ] 모든 길 토막에 `lengthM`, `widthM`, `type`, `queueAreaM2`, `stepFree`, `source`가 있다
  - [ ] 좌표가 올림픽공원 근처다 (위도 약 37.51~37.53, 경도 약 127.11~127.14)
- [ ] `routes.json`: A·B·C 세 방면 모두 KSPO DOME 모든 출구에서의 경로가 있고, 길 토막이 순서대로 이어진다
- [ ] `parking.json`: P1~P7 확인 결과가 반영되어 있고, 모든 주차장이 출구 1개 이상과 연결되어 있다
- [ ] `assumptions.json`: 모든 값에 `notes` 근거가 적혀 있다
- [ ] `docs/methods/network.md`에 데이터 출처, 측정 방법, 가정값 근거, 한계가 적혀 있다
- [ ] (가능하면) 계산 결과를 공연 날 실제 승하차·인구 데이터와 비교한 검증 결과가 있다

## 6. 추천 진행 순서

1. **뼈대 먼저** — 출구 → 중앙 분기점 → 3개 역만 있는 단순한 길(점 10개 안팎)을 대략적인 값으로 만들어 넘기기. 이것만 있어도 계산과 화면이 돌아갑니다.
2. **폭·길이 실측** — 주요 길부터 유효 폭과 줄 설 공간 측정
3. **주차장·차량 출구** — `parking.json`과 교차점
4. **가정값 근거** — 문헌 찾아 `assumptions.json` 보정
5. **세밀하게** — 길 토막을 더 잘게 나누고 다른 공연장 추가
6. **검증** — 계산 결과와 실제 데이터를 비교해 가정값 조정 (통합 담당과 함께)

## 7. 함께 맞춰야 할 사람

- **통합 담당:** 결과 파일 모양, 계산 결과가 현실적인지 함께 확인 (가장 자주 맞춰 볼 사람)
- **팀원 A:** 방면 A·B·C의 정의, 통제 구간 공지에 나오는 길이 어느 길 토막인지
